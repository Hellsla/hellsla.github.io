# Pipeline, review rule and CI scoping (from CLAUDE.md 'Pipeline')

Siirretty `fysiikkalabra/CLAUDE.md`:stä sellaisenaan (työjono 0b, 2026-11-17). Kaikki tämän tiedoston säännöt ovat voimassa; CLAUDE.md:ssä on niiden lyhyt muoto ja viite tähän tiedostoon. Sisältö on englanniksi kuten alkuperäinen.

## Pipeline
- `/practice <COURSE>` (`.claude/commands/practice.md`) writes and reviews a course's Sovella itsenäisesti tasks from `practice.py packet` files; their reviews are in `content/fi/<COURSE>/sovella/review/` and gate `site/<COURSE>-sovella.html` like a lesson's.
- **developer** writes and fixes, **science-reviewer**, **pedagogy-reviewer** and **visual-editorial-reviewer** (teacher 2026-10-31: figures, graphs, mathematical typography, Finnish, presentation, judged from the rendered captures) judge independently; each works from a packet file (`scripts/review_packet.py`) that its prompt names. `docs/EDITORIAL_QUALITY_STANDARD.md` is the shared yardstick (ten dimensions, 1–5 rubrics, Critical/Major/Minor); `/quality-audit <id> --audit-only|--fix` (`.claude/commands/quality-audit.md`) audits existing content of any type and corrects it through the same gate. `/lesson <id>` (`.claude/commands/lesson.md` at the repository root, beside `.claude/agents/`: routing, budgets, steps) runs a round; `/exercises <id> <task>` (`.claude/commands/exercises.md`) works on a lesson's exercises alone, from an exercise packet that carries the lesson's formulas and worked example (the exercise brief) instead of the lesson; `python scripts/check_lesson.py <id>` runs every deterministic check before any review, the lesson's translation check too (`check_i18n.py --lesson <id>`: every language that has the lesson translated, its numbers, formulas, structure and courses.json title; teacher 2026-11-17, after fy8-6's translation error was found only in CI).
- **Physics accuracy** (teacher 2026-10-28, after the FY1–FY3 audit): `docs/physics-guardrails.md` is the short physics reference every developer and science-reviewer packet carries (findings A error, B unstated condition, C fair simplification; one explanation worded the same everywhere it appears). `scripts/physics_phrases.py` warns in the lint about known wrong claims taught as fact and `test_physics_phrases.py` keeps them out in CI; `scripts/concepts.py` gathers one concept's sentences from every chapter for a cross-chapter science review when a change touches a concept in several chapters. The audit record is `docs/audits/fy1-fy3-physics-audit.md`.
- **The rule** (`scripts/reviews.py`): a lesson is on the site when all three reviews say PASS for its current content hash. Content published before the visual reviewer existed stays on the site under the hash-bound **visual baseline** (`docs/visual-baseline.tsv`, never added to by hand) until its first material change, which then needs a genuine visual PASS; `reviews.py baseline` lists what still awaits that review. Its exercise set has its own hash and its own three reviews (`exercises/review/`, `--exercises`): the page shows the version they last passed, so new exercises never take the lesson off the site. The hash covers the lesson files, its simulation folder, its pictures and its simulation tests; formatting, build scripts, templates and configuration never stale a review. What changed decides who looks again (`reviews.py scope`: none, delta or full per reviewer); a PASS that holds over a change its reviewer need not see is recorded in `review/carry.tsv` (`reviews.py carry`) and re-derived by CI. **A text change the teacher approved** (teacher 2026-11-13, work queue 8k): after the teacher has read a change of a lesson or exercise text (`.md`, `.json`; never code, a simulation or a picture) and approved it explicitly, `reviews.py approve-text <id> [--lang <l>] [--exercises] [--base <ref>] --source "<who approved what, when>"` records each changed file in `docs/teacher-text.tsv` (the hashes of its text before and after, the source of the approval; the command refuses without a source). That exact change is the category `teacher-text` (none for all three reviewers; `carry` records it, `verify` re-derives it). Any other change in the chapter is classified as usual, and an edit after the approval changes the hash, so the row no longer applies. **Figures the teacher approved** (teacher 2026-11-10: "kuvat olen itse hyväksynyt"; new ones are checked for layout only) need no science, pedagogy or visual review: after the teacher has seen them, `reviews.py approve-figures <id>` records each figure's exact Finnish drawing in `docs/teacher-figures.tsv`, and the change (the drawing, its words in a translation, a task given it by `"figure"`) is the category `teacher-figure`; `check_layout.py` checks the pages. Any later change to the drawing or its shared style needs a new approval. **The same carry for an investigation, a unit, a TVT guide, a Sovella set and an example exam** (teacher 2026-11-11, "laajenna kevyt hyväksyntä"): `reviews.py carry-item investigation|sovella|koe|unit|guide <id> [--lang en]` writes the part's `review/carry.tsv` when nothing but teacher-approved figures differs from the version the reviewers passed (texts with those figures' SVGs taken out, every other figure as drawn then and now); `verify` re-derives it in CI. Record an approval row only for a figure the teacher has seen: `approve-figures <id>` approves every figure of a lesson at once. **A simulation's change that only places or draws** (teacher 2026-11-11: an axis name or a label moved, nothing of the model, the computation, the sim's state or the teaching) is the category `presentation-only` (science and pedagogy carry over, the visual reviewer looks at the diff, `test_sims.py` runs as always), and only when both hold: `reviews.py presentation_only` accepts every changed line (drawing and placing calls, new local names; no assignment to anything else, no simState, adapter, control, event, time or other function call), and `docs/presentation-only.tsv` has the row of exactly this change (`reviews.py approve-presentation <sim.js> [<base>]` prints the diff and writes it; the teacher approves the row by merging the pull request). Anything else in a `sim.js`, or anything unclear, is `simulation` as before: full science and pedagogy reviews. There are no status fields and nothing to edit by hand. `review/legacy.md` marks a prototype lesson published before this pipeline until any content change retires it.
- Merging the pull request is the teacher's publication decision. CI rebuilds `site/` and fails if the committed copy differs; a lesson whose reviews went stale is left out with a WARNING, never silently.
- **CI tests only the changed pages** (teacher 2026-11-01, "testaa vain muuttuneet sivut"): on a pull request the three browser steps (`test_sims.py`, the per-lesson inquiry tests, `check_layout.py` at eight widths: about 1 h 30 min of a full run) test only the pages the change can alter, as `scripts/ci_scope.py` names them (a lesson's, investigation's, guide's or Sovella set's own files in any language, its simulation tests, the assets it uses, its sim texts in `lang/`, and every page whose committed `site/` HTML changed, so a neighbour whose chapter links changed is tested too). A change to anything shared (`scripts/`, `templates/`, shared `site/` files, `curriculum.json` and the other configuration, other `lang/` texts, `docs/visual-baseline.tsv`, the workflow) runs them in full, and so do main, the weekly run and a manual run (Actions → fysiikkalabra-ci → Run workflow). All other checks always run in full. Keep a pull request to one module or a few chapters so its run stays short; before pushing, run the same browser checks locally for exactly the pages `python scripts/ci_scope.py origin/main` prints, in CI's browser: `python scripts/ci_env.py run <command>` (CI's image, the Playwright that `requirements-ci.txt` pins, the same Chromium and fonts; work queue 5, 2026-11-16). `pip install -r requirements-ci.txt` installs the versions CI uses. A page whose only change is its `?v=` cache tokens is not a changed page. A new kind of file that changes a page needs its row in `ci_scope.py` (unknown files mean a full run, never a skipped test). A newer push to a pull request cancels its older run. The run is several jobs (2026-11-11, `scripts/ci_parallel.py`): three jobs of the other checks, and the browser checks page by page in their own jobs, two pages at a time so that each browser keeps the cores it had alone (a full run: eight simulation jobs, two layout jobs per width, four inquiry jobs; about 20 core-hours in all); the required check `qa` passes only when every job passed and the jobs' reports show every planned page tested exactly once. A new browser check gets its jobs the same way, never a step that tests the whole site in one job; more speed comes from more jobs, never from more than two browsers on a runner.
- **A shared change tests a sample, not the site** (teacher 2026-11-11): a push to `main` is scoped like a pull request, against the commit `main` had before the push (`github.event.before`). A change to a script, a template, the style sheet or the workflow tests the twelve pages of `ci_scope.py` `SMOKE` plus the lessons the change names by their own sources; the review system's own files (`scripts/reviews.py`, its tests, `docs/presentation-only.tsv`) test no page, their unit tests and `reviews.py verify` run in every run. The whole site is tested by the weekly run and by a manual run (Actions → fysiikkalabra-ci → Run workflow); if the comparison fails the run is full.
