---
description: Take one lesson from its curriculum slot to a reviewed draft pull request (packets by reference, three independent reviews by what changed, measured usage)
argument-hint: <lesson-id> [--warn 300000] [--limit 450000]
model: sonnet
effort: medium
---
Run lesson $ARGUMENTS through the pipeline. Work in `fysiikkalabra/` (`cd fysiikkalabra` first): every path below is relative to it. You coordinate; the agents do the work from packets. Read only the scripts' output and the agents' reports; never open a packet or a lesson file yourself.

**Routing** (the agent types `developer`, `science-reviewer`, `pedagogy-reviewer` and `visual-editorial-reviewer` are defined in `.claude/agents/` at the repository root; pass `model` and `effort` on every Agent call; if a type is not registered in this session, run a general-purpose agent with the same model whose prompt starts `Read .claude/agents/<name>.md and follow it as your instructions.`; say in the PR which model ran each step and why):

| step | agent | model, effort |
|---|---|---|
| this orchestration | — | Sonnet (this command's `model`) |
| draft, fix | developer | Sonnet medium. Opus medium only for a new numerical model (time integration, particle dynamics, a quantity that must emerge from the simulation), physics the course has not used before, or after a Sonnet attempt failed `check_lesson.py` twice or a science review found physics errors in its work. A simulation alone is not a reason: interface, layout, labels, colours, the adapter and test assertions stay Sonnet. Opus high only after Opus medium failed; Fable never without the teacher's word. |
| science review | science-reviewer | Opus medium |
| pedagogy review | pedagogy-reviewer | Sonnet medium |
| visual & editorial review | visual-editorial-reviewer | Sonnet medium (never Opus: it judges presentation and language; a doubt about physics goes to the science reviewer as a Polish note) |

**Prompts.** An agent's prompt is one line naming its packet, never the packet itself: `Read <path printed by review_packet.py> and follow it. Lesson: <id>. Mode: <mode>. Round: <n>.` For a fix, add one line: `Polish to fix: <ids, or none>.` and, after a failed check, the failing lines of `check_lesson.py`.

**Budget.** Warning 300 000 and hard limit 450 000 per lesson unless `--warn`/`--limit` say otherwise, counted as the sum of the agents' final context sizes the task notifications report (the measure every earlier run used; typical: draft 80–150 k, full review 50–110 k, fix 30–60 k, delta review 15–30 k). Past the warning, say so in the PR and continue; past the hard limit, stop safely: finish nothing half-way, commit what exists, and open the draft PR with a "Kesken" section saying which review or fix remains. Never shorten or skip a necessary review or correction to stay under a number.

0. `python scripts/courses.py init-lesson <id>` (meta.json from the curriculum slot; if the course is not initialized, tell the teacher to run `/new-course <course>` and stop).
1. If the folder has no `lesson.md`: `python scripts/review_packet.py <id> --role developer`, then the developer ("draft").
2. `python scripts/check_lesson.py <id>`: lint (complete solutions included, `check_solutions.py`) (with the page rules of CLAUDE.md "Lesson page", errors on a lesson being written or edited), LaTeX, build, simulation tests, inquiry tests with the page form at 360, 1280 and 1920 px, answer positions, 360 px. On FAIL run the developer with `--role developer --fix` and the failing lines; at most twice.
3. `python scripts/screenshot.py <id> --if-stale` (once the content is stable; unchanged captures are reused), then `python scripts/reviews.py scope <id>` and `python scripts/reviews.py scope <id> --exercises` (the exercise set has its own reviews, README "Exercises"). A reviewer whose mode is `none` (the change is outside its judgement) is not run: `python scripts/reviews.py carry <id>` (`--exercises`) records that its PASS (or the visual baseline) carries over. For the others `python scripts/review_packet.py <id> --role science` / `--role pedagogy` / `--role visual` and the reviewers as parallel subagents (at most three, one of each kind, never two visual reviewers on the same content); each sees only its own packet, never another's report. When the lesson's review is full and the exercises need a full one too (a new lesson), that packet asks for both reports in the same run. A visual reviewer must look at the captures: a visual report whose Checked section names no capture is sent back. Exercises that need a review the lesson packet does not ask for get their own packets (`--exercises`), as in `/exercises`. Then `python scripts/reviews.py status <id>`.
4. If the lesson and its exercises are both `reviewed`: go to 6. If a report says `ESCALATE`: commit, regenerate that packet, and if it is still delta add `Full review required.` to the prompt. If a report says FAIL: classify every finding (Blocking and Polish) as **A** scientific/pedagogical, **B** usability/accessibility/presentation (the visual reviewer's Critical and Major findings are B unless they concern physics) or **C** cosmetic. Run the developer with `--fix`, naming the A and B Polish items; C items go to the PR only. Then from step 2; in the next round only the reviewers whose scope is not `none` run again (a cosmetic fix: visual delta, the others carried). At most three review rounds; after the third, stop and report what remains.
5. Commit after each round's reviews and before a fix, so the next scope finds the reviewed version: `git add content lessons tests/sims glossary.json assets && git commit -m "fysiikkalabra: <id> round <n>"`.
6. Finish: `python scripts/usage.py collect <id> --round <n>` (measured tokens and cost of every agent and of this session's share; nothing from the transcripts but numbers), `python scripts/build.py --all`, `python scripts/build.py`, commit `site/` and `review/`, push the branch `claude/lesson-<id>`, and open or update the draft pull request: **Oppitunti** (id, title, one sentence, what changes on the site, build WARNING lines); **Tarkistukset** (the last `check_lesson.py` lines, the verdicts with hashes, carried-over reviews and why, CI link); **Kierrokset** (rounds, Blocking findings fixed, A/B Polish applied, C left); **Kulutus** (`python scripts/usage.py report <id>`, and the model of each step with its reason); **Vaikutus** (`python scripts/reviews.py impact origin/main`); **Opittua** (rules or tests added); **Avoimet kohdat**. Merging is the teacher's publication decision: never merge, never push to `main`.

**Batch.** When one small change of the same kind goes to many lessons (a law named, a sim text moved into its boxes, figures recoloured line for line, formulas re-set; all classified by `reviews.py scope` as delta or none), run it as one batch instead of a /lesson per lesson: the developer per lesson with a narrow prompt, `check_lesson.py` per lesson, `screenshot.py <id> --if-stale` per lesson, then `reviews.py carry` for every lesson whose reviewer is `none`, `python scripts/review_packet.py --batch <id>,<id>,... --role science` / `--role pedagogy` / `--role visual` and ONE reviewer of each kind (prompt `Read review-batch/packet-<role>.md and follow it. Lessons: <id>, <id>, .... Mode: delta. Round: 1.`), which writes each lesson's own report. `usage.py collect <id>,<id>,...` shares the batch runs among the lessons. A lesson the scope puts in full review leaves the batch for a /lesson of its own.

**Physics consistency** (teacher 2026-10-28, `docs/physics-guardrails.md`). Packets carry the guardrails; the lint prints `physics [...]` warnings the science reviewer judges. Before opening the PR run `python scripts/concepts.py changed`: for each concept the change touches in more than one chapter (a concept-wide correction), run `python scripts/concepts.py packet <concept>` and ONE science-reviewer (Opus medium) with `Read review-concepts/packet-<concept>.md and follow it.`; fix its contradictions in the lessons they name (a batch delta review covers those edits). A single lesson's change needs no concept review.

**Simulations.** The developer creates the lesson's own folder (`assets/sims/<course>/<id>/`), reuses one the course already has (`"sim": "<name>"` in meta.json) or modifies one. Modifying a folder another lesson uses re-opens that lesson's reviews too (`reviews.py impact` lists them): do it only when the packet's task or the teacher says so, and name every affected lesson in the PR.

**Assessment and visuals before adding** (teacher 2026-10-29). Before a developer writes or adds checks or tasks: `python scripts/assessment.py <COURSE>` and `python scripts/coverage.py <COURSE>` (which goals are already assessed, which concepts lack a check), then reuse, convert an exit-ticket question or replace a weak task before adding one; not every goal needs a multiple-choice check. Look for a meaningful image-dependent task per chapter with `python scripts/figcat.py find …` (reuse a figure or a question-safe variant; never decoration, never SVG in a packet). Learning goals complete their heading ("laskemaan …"; `scripts/objectives.py`), so a goal rephrased only for grammar is category `objective-form` (pedagogy delta, no science review).

**Learning loop.** When a finding is an objectively testable, recurring error: fix it, then add a check (`lint_lesson.py`, `test_sims.py`, `check_layout.py`, `test_inquiry.py`) with a test that catches the original case and passes on every other lesson; if it is not testable, add one dated line to `NOTES.md` under the right heading, with the lesson id (`(2026-11-02, fy4-3)`). Mention it in the PR.

**Visual & editorial review** (teacher 2026-10-31, `docs/EDITORIAL_QUALITY_STANDARD.md`). The third reviewer judges illustrations, graphs, mathematical typography, Finnish and presentation from the captures; it never replaces the science or pedagogy reviewer. A lesson published before 2026-10-31 sits on the visual baseline (`docs/visual-baseline.tsv`) until its first material change: then `scope` puts the visual reviewer in full, once, and its PASS is required like the others'. `python scripts/reviews.py baseline` lists what still awaits that review; `/quality-audit <id>` runs it without a content change.
